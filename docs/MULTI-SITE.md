# Multi-site CMS

One Strapi instance can publish a **primary** site plus any number of **secondary** sites. The Next.js app resolves the active site from the request `Host` header and loads only that site’s pages, navigation, brand, and **theme**.

There is **no schema cap** on secondaries. Prefer a small number in production for DNS, TLS certificates, and CORS maintenance.

## Model

| Content type | Notes |
| --- | --- |
| **Site** | Hostname(s), `key`, `template`, `theme`, brand/contact/SEO |
| **Page** | Required `site` relation; slug unique **per site** |
| **Navigation** | Collection type; one published nav document per site per locale |
| **Global** | Deprecated — kept only for migration; prefer Site brand fields |

### Site fields (admin)

- **name** — admin label (localized)
- **key** — stable UID used by the frontend (`santamar`, …)
- **hostname** — exact host match, no protocol (`www.example.com`)
- **hostnames** — optional JSON/array of aliases (`example.com`, `www.…`)
- **isPrimary** — at most one primary (enforced in lifecycle)
- **template** — `multi_page` (classic routes) or `single_page` (one long page + hash nav)
- **theme** — `coastal` \| `harbor` \| `dune` (existing visual theme tokens; applied by the frontend)

### Resolve API

```http
GET /api/sites/resolve?host=www.example.com&locale=en
```

Matches `hostname` or any entry in `hostnames`. For `localhost` / `127.0.0.1`, falls back to the primary site when no exact match exists.

Public permissions: `site.find`, `site.findOne` (resolve route is `auth: false`).

## Provision site (recommended for secondaries)

Use the **Provision site** menu item in the Strapi admin (left nav). Fill in:

| Field | Notes |
| --- | --- |
| Site name | Becomes admin label, brand `siteName`, and the `key` UID |
| Hostname | Exact Host match (no protocol) |
| Template | `multi_page` or `single_page` |
| Theme | `coastal`, `harbor`, or `dune` |

Click **Create site & deployment pack**. That calls admin `POST /sites/provision`, which:

1. Creates and publishes the Site (`isPrimary: false`).
2. Creates starter pages + navigation for that template only.
3. Writes a deployment pack under [`sites/<key>/`](../sites/) (see below).
4. Returns the assigned port, pack path, and a CORS reminder.

Duplicate `key` or hostname is rejected (HTTP 409).

### Manual workflow (Content Manager)

You can still create Sites by hand under **Content Manager → Sites**, then add pages/nav yourself. Prefer **Provision site** when you also want the Next process pack.

Seed only creates the primary **santamar** site (`PRIMARY_HOSTNAME`, default `localhost`, theme `coastal`).

## Themes

Each Site has a `theme` enum matching the frontend packs in [`frontend/src/theme/`](../frontend/src/theme/):

| ID | Character |
| --- | --- |
| `coastal` | Atlantic teal, glass header (default) |
| `harbor` | Ink & brass, solid header |
| `dune` | Warm sand & olive, minimal header |

The locale layout passes `site.theme` into `AppThemeProvider`. In production the CMS value wins. With `NEXT_PUBLIC_ENABLE_THEME_SWITCHER=true`, the floating switcher may override via localStorage for local experimentation.

## Templates

### `multi_page`

Header links to locale-prefixed paths (`/en/accommodations`). Nav items: `targetType: page` with `url` and/or related `page`.

### `single_page`

Only the **home** page is served. Extra slugs 404.

1. Put the full scroll narrative in the home page **sections** (order matters).
2. In Navigation, set items to `targetType: section` and a **sectionAnchor**.
3. Section anchors map to page sections **in the same order** as section-type nav items.
4. Header links become `/en#stay` with smooth scroll; active state uses `IntersectionObserver`.

Provision’s `single_page` starter includes hero / stay / location / book / contact sections and matching section nav.

## Deployment packs (`sites/<key>/`)

Generated by Provision site. The shared Next app in `frontend/` is the only site codebase — packs do **not** copy `src/`.

| File | Purpose |
| --- | --- |
| `.env` | `SITE_KEY`, `SITE_HOSTNAME`, `PORT`, `NEXT_PUBLIC_STRAPI_URL` |
| `ecosystem.config.js` | PM2 app `santamar-web-<key>` running `npm start` in `frontend/` |
| `apache.conf` | Apache vhost → `127.0.0.1:<port>` with `ProxyPreserveHost` |
| `nginx.conf` | Nginx server block with `Host` / `X-Forwarded-Host` |
| `README.txt` | Operator steps (CORS, PM2, local dev) |

**Ports:** start at **3100**, skip ports already listed in other `sites/*/ecosystem.config.js` files. Port **3000** stays the shared/dev app in [`deploy/ecosystem.config.js`](../deploy/ecosystem.config.js).

Pinned `SITE_KEY` means that process serves only its Site. An unpinned shared process still resolves by `Host`.

```bash
# Production
pm2 start sites/<key>/ecosystem.config.js

# Local, pinned to this site
set -a && source sites/<key>/.env && set +a
cd frontend && npm run dev
```

After provisioning, add the public origin to `FRONTEND_URLS` in `cms/.env` and restart Strapi. Override pack location with `SITES_ROOT` if needed.

## Frontend resolution

1. Middleware reads `Host` / `x-forwarded-host`, strips the port, and sets request header `x-santamar-site-host`.
2. Locale layout calls `getSiteByHost` → `/api/sites/resolve`, then loads site-scoped nav and applies `site.theme`.
3. Unknown hosts **404** in production. In development (or with `SITE_FALLBACK_PRIMARY=true`), the primary site is used.

### Env

| Variable | Where | Purpose |
| --- | --- | --- |
| `PRIMARY_HOSTNAME` | CMS | Hostname written on the seeded primary Site |
| `SITES_ROOT` | CMS | Where provision writes packs (default `../sites` from `cms/`) |
| `FRONTEND_URL` / `FRONTEND_URLS` | CMS | CORS origins for each public site |
| `SITE_FALLBACK_PRIMARY` | Frontend | Force primary fallback when host is unknown |
| `SITE_KEY` / `SITE_HOSTNAME` | Frontend process | Pin one site (deployment packs set these) |
| `NEXT_PUBLIC_EMBED_SCRIPT_ALLOWLIST` | Frontend | Host suffixes allowed for CMS-pasted booking embed scripts (default `cloudfront.net`) |

## Booking embeds (Hostaway)

Editors paste the **full** Hostaway snippet into page sections — do not map individual widget options in Strapi.

| Block | Use |
| --- | --- |
| **Booking Search** | Hostaway search / booking bar (`widget.js` + `searchBar(...)`) |
| **Booking Calendar** | Hostaway availability calendar (`calendar.js` + `hostawayCalendarWidget(...)`) |
| **Booking CTA** | Simple marketing button (URL link) — not an embed |

Workflow:

1. Copy the embed HTML/JS from Hostaway (div + script tags).
2. In Strapi, add **Booking Search** or **Booking Calendar** to a page’s sections.
3. Paste into **Embed code**; optional **Title** for the section heading.
4. Publish and rebuild the static frontend if you use LAMP export.

Safety on the frontend:

- Markup is sanitized (scripts stripped from HTML) before mount.
- External `<script src>` hosts must match `NEXT_PUBLIC_EMBED_SCRIPT_ALLOWLIST` (default: `*.cloudfront.net`).
- Inline init scripts run only after allowlisted scripts load, via real `<script>` elements (not `eval` of the raw paste).
- Only authenticated CMS users can edit embed code.

## Deploy notes

- **Separate Next processes** (recommended for secondaries from Provision): one `frontend` build, many PM2 apps with different `SITE_KEY` / `PORT` / vhosts — see packs above.
- **Single multi-tenant process**: one `next start` that resolves every hostname via `Host` (no `SITE_KEY`).
- **Static LAMP export**: one build still equals one site (`SITE_KEY` / `SITE_HOSTNAME` at build time). See [DEPLOY-LAMP-STATIC.md](./DEPLOY-LAMP-STATIC.md).

## Ops guidance

Keep secondaries few enough that you can manage DNS, certificates, CORS, and PM2 processes without drift. The CMS does not limit how many Site entries you create.
